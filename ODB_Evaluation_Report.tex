\begin{abstract}
This document presents the full experimental setup and evaluation protocol for On-Demand Buffer (ODB). Our goal is to demonstrate that ODB eliminates the per-request CPU cost associated with data copying in multi-tier applications. The evaluation is conducted on the Grid'5000 testbed using a 4-tier architecture. We contrast a baseline standard Java servlet with our ODB-optimized implementation across a wide range of payload sizes.
\end{abstract}

\section{Introduction and Theoretical Foundation}
\selectlanguage{french}
L’objectif de notre contribution, On-Demand Buffer (ODB), est de proposer une solution zero-copie transparente pour les applications multi-tier. ODB intercepte les appels système d'E/S (\texttt{write}, \texttt{read}) pour éviter le transfert physique des données lorsque celles-ci ne sont pas exploitées par les nœuds intermédiaires.

Le principe repose sur trois piliers :
\begin{enumerate}
    \item \textbf{Données Virtuelles} : Au lieu d'envoyer la payload réelle, ODB émet un descripteur (\texttt{odb\_desc}) de petite taille ($\approx 1$KB).
    \item \textbf{Interception Transparente} : ODB utilise les mécanismes de protection mémoire du noyau pour détecter les accès aux données.
    \item \textbf{Récupération à la demande} : Les données ne sont rapatriées que si une faute de page est déclenchée par l'application.
\end{enumerate}
\selectlanguage{english}

\section{Experimental Infrastructure}

\subsection{Node Characteristics and Platform}
Evaluations are conducted on the \textbf{Grid'5000} large-scale testbed, specifically on the Grenoble site using \texttt{dahu} and \texttt{gros} clusters. These clusters provide bare-metal access to Dell PowerEdge servers.

\begin{itemize}
    \item \textbf{Hardware Architecture}: x86\_64 (Intel Xeon).
    \item \textbf{Network Connectivity}: 10 Gbps Ethernet between all nodes, providing a high-bandwidth backplane essential for 1MB payload testing.
    \item \textbf{Operating System}: Debian 11 (Bullseye) / Ubuntu 22.04 LTS.
    \item \textbf{Java Runtime}: OpenJDK 21 (required for Tomcat 11 and ODB bytecode features).
    \item \textbf{Shared Storage}: All nodes utilize a site-wide NFS share (\texttt{/home/<user>/mesures}) ensuring consistent application binaries and datasets.
\end{itemize}

\subsection{4-Tier Architecture Mapping}
We utilize four physical nodes to replicate a realistic production pipeline. \textbf{Scientific Choice}: While a 3-tier setup is simpler, it often merges the Load Balancer and Proxy roles. By separating them, we ensure that M3's CPU is consumed only by the Java Servlet logic and kernel packet processing, without being contaminated by Nginx's connection management.
\begin{description}
    \item[M1 - Client (Load Generator)]: Orchestrates the tests and runs \texttt{wrk2}.
    \item[M2 - Load Balancer]: Runs Nginx as a reverse-proxy. It simulates a modern entry point for distributed systems.
    \item[M3 - Proxy Server (SUT)]: Runs Tomcat 11.0.1 with the servlet under test. This is the bottleneck node we aim to saturate.
    \item[M4 - Backend Server (Storage)]: Runs Tomcat 11.0.1 and hosts the original image files.
\end{description}

\subsection{Node Characteristics and Hardware Bridling}
To perform a high-resolution observation of CPU saturation, we apply specific hardware restrictions on the Proxy node (\textbf{M3}):
\begin{itemize}
    \item \textbf{Network}: 10 Gbps Ethernet interfaces. Theoretical throughput limit is $\approx 9.4$ Gbps.
    \item \textbf{CPU Restriction}: Although the physical nodes possess 64 cores, we restrict M3 to exactly \textbf{4 active cores}.
    \item \textbf{Mechanism}: CPUs 4 to 63 are disabled at the kernel level to ensure that the workload is concentrated on the first 4 cores, making it easier to observe 100\% saturation.
\end{itemize}

\section{System Preparation and Configuration Procedures}

\subsection{Deployment Sequence}
The deployment is performed manually to ensure environmental consistency:
\begin{enumerate}
    \item \textbf{Backend (M4)}: Start Tomcat and verify local file serving.
    \item \textbf{Proxy (M3)}: Apply kernel tuning, core restriction, and start Tomcat in proxy mode pointing to M4.
    \item \textbf{Load Balancer (M2)}: Configure Nginx sites and restart the service after clearing port 8080.
    \item \textbf{Client (M1)}: Execute the Python automation script.
\end{enumerate}

\subsection{Rationale for Scientific Choices}
To ensure the reproducibility of our findings, we justified each technical constraint:
\begin{itemize}
    \item \textbf{4 Restricted Cores}: By disabling 60 out of 64 cores, we create a computational bottleneck that can be reached using a standard load generator (M1). Without this, the 10Gbps link would saturate before the CPU, masking ODB's efficiency gains.
    \item \textbf{Keep-Alive mandatory}: Moving from 3 to 4 nodes revealed a significant latency penalty due to TCP handshake overhead. We chose to enforce persistent connections to isolate the application-layer performance.
    \item \textbf{Normalization of CPU Cost}: Comparing raw CPU usage is misleading if the throughput differs. We use \textit{CPU \% per 1000 RPS} to provide a linear comparison of "effort per request".
\end{itemize}

\subsection{OS/Kernel Tuning}
To prevent requests from being dropped before they reach the application, we optimize the Linux network stack on all nodes:
\begin{itemize}
    \item \texttt{net.core.somaxconn = 1024}: Increases the listen queue size.
    \item \texttt{net.core.netdev\_max\_backlog = 2000}: Increases the packet input queue.
    \item \texttt{net.ipv4.tcp\_max\_syn\_backlog = 1024}: Expands the SYN backlog.
\end{itemize}

\subsection{Nginx Optimization (M2)}
A crucial step in our 4-tier setup was the discovery of the \textbf{"TCP Tax"}. Without persistent connections, M3 wasted $\approx 15\%$ of its CPU just opening and closing TCP sockets.
\textbf{Configuration choice}: We enabled HTTP/1.1 Upstream Keep-Alive in Nginx to ensure that M3's CPU is dedicated solely to servlet processing.

\subsection{Tomcat Optimization (M3/M4)}
To handle high RPS ($>40,000$), Tomcat was tuned via \texttt{server.xml}:
\begin{itemize}
    \item \texttt{maxThreads="1000"}: Ensures enough workers are available.
    \item \texttt{acceptCount="1000"}: Prevents connection refused errors during bursts.
    \item \textbf{AccessLogValve}: Disabled to eliminate Disk I/O Wait that artificially lowers CPU usage.
\end{itemize}

\section{Evaluation Strategy}

\subsection{Workload}
A pool of 50 sampled images in addition to the 4 reference base images, totaling 54 test cases, ranging from \textbf{1.3KB to 1MB} is used to test the sensitivity of both implementations to data size.

\subsection{RPS Ramping and Adaptive Precision Detection}
The system uses an adaptive strategy starting at 500 RPS. The load is increased using coarse-grained steps (e.g., 5000 RPS). To find the exact limit intelligently, we implement an \textbf{Adaptive Precision Phase}. The load is increased until one of the following "Physical Saturation" points is reached:
\begin{itemize}
    \item Achieved RPS < 90\% of target RPS.
    \item CPU utilization on M3 > 95\%.
    \item Network throughput > 9.4 Gbps.
    \item Average latency > 500 ms.
\end{itemize}

Once saturated, the script enters a \textbf{Precision Refinement} mode. It performs a finer-grained sweep between the \textit{last stable RPS} and the \textit{saturated RPS} to pinpoint the exact \texttt{RPSmax} with higher resolution. This ensures that our results are not merely artifacts of the coarse step size.

\subsection{Fixed RPS Comparison}
To ensure fair comparison of latency, the script dynamically identifies the highest RPS that all payload sizes and servlets can maintain stably, then generates comparison plots at this specific fixed point.

\section{Evaluations and Scenarios}

\subsection{Evaluation A: Motivation - Standard Servlet Bottlenecks}
\textbf{Aims}: This evaluation serves as the baseline. It aims to visualize the physical limits of the system without ODB. We prove that as payloads grow, the bottleneck shifts from being computational to being bandwidth-bound.

\textbf{Setup}:
\begin{itemize}
    \item \textbf{Component}: Ordinary \texttt{Serv} (standard Java I/O).
    \item \textbf{Payloads}: 4 base images: \texttt{image\_1KB.jpg}, \texttt{image\_10KB.jpg}, \texttt{image\_100KB.jpg}, \texttt{image\_1000KB.jpg}.
    \item \textbf{Procedure}: For each image, we sweep the target RPS from 500 up to 40,500. We monitor CPU usage specifically on M3's 4 active cores.
\end{itemize}

\textbf{Why this choice?}: Using only 4 base images allows for a clear visualization of the "RPS vs. Size" inverse correlation.

\textbf{Results and Metrics}:
\textit{Expected metrics to be filled after run:}
\begin{itemize}
    \item \textbf{RPSmax}: The point where real RPS falls below 90\% of target.
    \item \textbf{Saturation Reason}: CPU limit for 1KB; Bandwidth limit for 1MB.
    \item \textbf{Node Monitoring}: Verify that M4 remains non-saturated while M3 hits 100\% CPU.
\end{itemize}

\subsection{Evaluation B: ODB CPU Efficiency and Bypass Proof}
\textbf{Objective}: Prove that ODB makes the per-request CPU cost independent of the payload size. This is the core validation of the "Zero-Copy" claim.

\textbf{Metric}: CPU \% per 1000 requests (Efficiency).

\textbf{Continuous Justification}: We do not use raw CPU percentage as a primary metric because ODB achieves much higher RPS. A system running at 80\% CPU and 50,000 RPS is significantly more efficient than one at 80\% CPU and 5,000 RPS. By normalizing to "CPU cost per 1k requests", we reveal the true architectural advantage.

\textbf{Scientific Expectation}: If ODB truly bypasses the data via virtual descriptors, the cost of processing a 1MB file should be identical to the cost of a 1KB file ($\approx$ size of the descriptor).

\subsection{Evaluation C: Large-Scale Invariance (50 sampled images)}
\textbf{Objective}: Validate ODB performance stability across a massive set of payloads (1.3KB to 999.7KB) to ensure there are no "hidden" costs or corner cases in the descriptor handling.

\textbf{Setup}: We utilize a pool of 50 sampled images in addition to the 4 reference base images, totaling 54 test cases.

\textbf{Rationale}: Scientific results on a small number of samples can be subject to cache artifacts. By using 50+ distinct sizes, we provide a statistically significant "Invariance Proof" where ODB results should form a horizontal line, overlapping the baseline standard performance of a 1KB file.

\subsection{Evaluation D: Latency Stability at Best Common RPS}
\textbf{Objective}: Compare the tail latency (P99) of ODB vs. Standard at a fixed load level.
\begin{itemize}
    \item \textbf{Mechanism}: The script dynamically finds the highest RPS supported by ALL configurations and measures response times at that point.
\end{itemize}
